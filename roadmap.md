- **Phase 18 — Site identity closeout.** _(shipped)_ The Phase 17 review (2026-11-05) decided these:
  - The YouTube-check line stays hidden until the first real helper status arrives. `HealthController` starts with no helper status, so launch does not flash "missing".
  - A remote player-client name is kept only when it matches `^[a-z0-9_]+$`. Anything else is rejected and the previous order stays. The string is passed into the downloader's extractor arguments.
  - The named-site list uses the same names as the confirmation (`YouTube`, not `youtube`). An empty Only-these-sites list says that cookies go nowhere until a site is added. The scope control stays hidden until a browser is chosen.
  - `docs/state-flow.md` matches the client rule: the cached order plus the per-job burned set picks the client, not `attempt`. Restart with sign-in for an unlisted host under Only these sites is documented, and cookies follow the scope.
  - The copy audit walks every user-facing sentence (row remarks, toasts, dialogs, onboarding, Preferences, About, Diagnostics). The health chip that says `engine · current` / `engine · update available` says Downloader.
  - `PlayerClientRotation.client(forAttempt:)` is removed. It has no callers and ignores its argument.
  - `UserFacingJargonTests` reads the three health-chip labels from `HealthController`, not from literals compared with themselves.

- **Phase 21 — Release hardening.** _(shipped)_ Everything that can be proven before a release is published, proven on the built, signed app. Every pipeline step is a script in `scripts/release/` or `scripts/e2e/` that runs the same locally and in CI, and `release.yml` is a list of calls. A clean-environment end-to-end run on the built app (a temporary home, `PATH=/usr/bin:/bin`, no internet: every bundled tool, a download from a local fixture server, m4a and mp3 extraction, the sign-in helper starting and answering from inside the bundle, and in CI the app itself starting) is a required step before any release publishes, and `make e2e` runs it locally. The update path is proven by the feed and key check, an appcast signature check against the key inside the app, and the feed check after publishing; the in-place update between two real releases is a checklist item. `publish-release.sh` has a stubbed-`gh` test, and the feed check reverts the release to draft when the latest release's `appcast.xml` does not serve the released version. Licenses: a Preferences pane with a Read button per component, each opening its license text from the pinned source, the pinned FFmpeg, LAME and helper sources attached to every release, and a test that the FFmpeg build stays LGPL. `PRIVACY.md` lists every connection the app makes and a Privacy pane shows a committed plain-text copy kept in step by a test, `SECURITY.md` and an issue template are added, release notes are a hand-written plain-language file per version, `make release-*` runs the gate as a dry run before tagging, and a short release checklist that it prints covers what cannot be automated. The in-app mark becomes the one fixed Aurora orb under every theme, matching the Dock icon. Spec: `docs/superpowers/specs/archived/2026-11-17-media-grabber-phase-21-release-hardening-design.md`.
- **Phase 22 — Code cleanup.** _(shipped)_ Structure that has to be right before the app is released and tested as a whole. The first item is app locations: one `AppLocations` in `GrabberKit`, created once at launch, is the only code that reads the real home or the optional `MG_HOME`, and derives the logs, job-logs, queue store, Application Support and default Downloads locations. Components receive the narrow location they need, the `home:` defaults that point at the real home are removed, the uninstall list derives from the same value, settings use a separate named store when the override is set, and a test fails when code outside it reads the system home. The end-to-end script then sets `MG_HOME` and checks `app.launched` in the log. The dead parameters on the Shield installer go, and the launch-time yt-dlp version check runs through `ProcessRunner` asynchronously with a timeout, so the app-relaunch helper is the only other place that starts a process and is named as the exception in `CLAUDE.md`; it starts a detached waiter that opens the app only after this process has exited, so two copies never share the queue files. Other cleanup items are added here as they surface. Spec: `docs/superpowers/specs/archived/2026-11-20-media-grabber-phase-22-code-cleanup-design.md`.
- **Phase 23 — Review fixes.** _(in progress)_ Bugs found by the pre-release code review, fixed before the first release and after the structure cleanup so they land on the new locations. Findings are in `audit/report/2026-11-21-review-*.md`, one report per reviewed area, each verified against the code before it is acted on. Decided: a corrupt or newer-schema `queue.json` is backed up beside the original before a fresh file is written; a retry appends to the job's one log with an attempt marker, and log eviction runs. The scheduler, `recordExit` and shutdown findings read `docs/state-flow.md` first. An unclassified failure shows one plain sentence with the raw text behind a collapsed Details. A missing Firefox profile is not replaced by the default: a new verdict names it and offers a way to pick another. Deferred jobs do not hold a per-host slot. A playlist group's header counts done, failed, cancelled and in-progress children, hides zero counts, and a test pins each state to its wording. The Verbose logging setting drives the log level at launch and on change. The sign-in list in Preferences gets an add-site field so a site can be added there as well as from a failed row. The Developer links point at the MediaGrabber repository. Release builds have no Debug menu. After a failed uninstall the app says plainly that it needs to be reopened and offers a Relaunch button. The release scripts are fixed first, since a tag push cannot start a release today: the version is derived for the tag-push event with a test for it, the update feed keeps its earlier items, stale drafts are removed, source asset names are right, and the signature check says what is missing. The uninstall list covers everything the app saves. The uninstall dialog lists unfinished downloads under "Unfinished downloads". The helper's port is really checked and the helper is confirmed to be the app's own process, the release job's checkout keeps no stored credentials, and the link is passed to yt-dlp after `--`. Every first attempt goes without sign-in, and sign-in is used only when the failure is one that sign-in can fix; the sign-in scope setting decides on which sites that retry may use it. When a browser is chosen and the scope allows the site, the app retries once on its own with sign-in and the row reads "Signing in…" during that attempt; with no browser chosen the row fails with the Retry with sign-in button, which leads to setup. A job whose chosen browser cannot be read runs without sign-in, and if it then fails the message names the unreadable browser and offers a button to open the sign-in settings. Links that arrive from outside the app (the custom link scheme, Services, Share) still start the lookup at once, and `PRIVACY.md` lists those entry points. An updated downloader in Application Support is used only when its checksum matches the one recorded when the updater installed it. Quitting does not save stopped jobs as cancelled, a failed probe keeps its real cause and a transient one can be retried, and the permission and 403 messages are cause-specific. Detailed at its normal turn once every area is reviewed.
